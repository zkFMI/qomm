# 日銀型の国債決済、共通担保、日中当座貸越

## 1. 結論

日本銀行の公開資料に合わせるなら、DeFMIに「日銀があらかじめ資金を置く保証口座」を作るのは
正しくない。実務に近いモデルは次のとおりである。

1. 日銀は、参加金融機関の当座預金と国債振替を正本として管理する。
2. 適格担保は支店別ではなく、同じ法人の共通担保としてまとめて管理する。
3. 日中当座貸越の利用可能額は、共通担保の評価額から、他の日銀与信、既存の貸越残高、
   未約定の予約額を引いて求める。
4. 国債を買うときは、国債受領、共通担保への差入れ、必要な貸越、売り手への支払を一括で
   実行できる。
5. 担保中の国債を売るときは、売却代金の受領、貸越返済、担保返戻、国債移転を一括で
   実行できる。
6. 国債残高、担保余力、当座預金と貸越余力のどれかが不足すれば、一部だけを実行しない。
7. 日中貸越は当日終業時が期限である。日中は無利息だが、終業時に残高が残れば延滞扱いに
   なる [1]。

このため、QOMMで複数RFQが同時に成立し得る場合も、ウォレット単位ではなく法人単位の
共通担保余力を予約しなければならない。

## 2. 実際の日銀ネットで何が正本になるか

日銀は、国債振替決済制度と日銀当座預金を運営している。国債の権利移転は国債側の帳簿、
中央銀行マネーの移転は当座預金側の帳簿に記録される。国債の受渡しと資金支払を結び付け、
片方だけを成立させない仕組みが国債DVPである [2]。

したがって、正本台帳の内部で口座を一切指定しないわけではない。日銀は参加者と口座を把握する。
匿名化できるのは、外部へ公開する識別子、取引相手から見える情報、または複数DeFMI間で運ぶ
証明である。DeFMI実装では、外部APIには法人と口座の32バイト要約値を出せるが、合意状態の内部には
次の対応が必要になる。

- 法人の要約ID
- 当座預金口座の要約ID
- 国債口座の要約ID
- 共通担保に入っている国債ごとの状態
- 当座預金残高
- 日中当座貸越残高
- 他の日銀与信に必要な担保額
- 未約定の決済予約額
- 営業日、返済期限、状態の通し番号

この構造により、公開ネットワーク上で実名口座を出さなくても、正本側では同じ法人の全要求を
一つの余力へ集約できる。

## 3. 共通担保の評価

実装では、国債担保一件の評価額を整数演算だけで次のように求める。

```text
担保価額
= 額面金額
  × 額面100円当たりの時価
  ÷ 100
  × 物価連動係数
  × 日銀の掛目
```

端数は切り捨てる。時価、残存期間、担保の種類に応じた掛目は、日銀が公表する担保価格に対応する
[4][5]。物価連動国債でなければ物価連動係数は1である。

法人全体の利用可能額は次の式で求める。

```text
利用可能な日中流動性
= 共通担保の評価額合計
  - 他の日銀与信の所要担保
  - 日中当座貸越残高
  - 期限内の未約定予約額
```

値が負になる場合、利用可能額はゼロとする。時価または掛目の変更で担保不足になった場合、
既存債務を消したことにはしない。新規貸越と担保返戻を止め、返済または追加担保による解消を
待つ [7]。

## 4. 国債を買う場合

買い手が国債を受け取り、その国債を直ちに共通担保へ入れる場合の一括更新は次のとおりである。

```text
事前状態
  買い手: 当座預金、既存共通担保、既存貸越、予約
  売り手: 対象国債

一括判定
  1. 対象国債が売り手にあり、二重ロックされていない
  2. 買い手と資金支払人が同じ法人である
  3. 対象国債が適格で、最新の時価・掛目を持つ
  4. 買い手の当座預金不足額を計算する
  5. 受取国債を共通担保へ加えた後の余力が不足額以上である
  6. 予約を使う場合、予約の指図要約、期限、法人、金額が一致する

一括更新
  国債を売り手から買い手へ移す
  → 買い手の共通担保へ入れる
  → 当座預金不足額だけ日中貸越を増やす
  → 売り手へ代金を移す
```

買い手の当座預金だけで支払える場合、貸越額はゼロである。国債の担保差入れ自体は行える。
受け取る国債を担保にし、必要ならその場で日中貸越を行う取扱いは、日中当座貸越基本要領に
明記されている [1]。

## 5. 担保中の国債を売る場合

売り手が担保中の国債を売る場合は、国債を先に自由化すると一時的な担保不足を作り得る。
そのため次を一括で計算する。

```text
売却代金を受け取る
→ 売り手の日中貸越を先に返済する
→ 返済後に残る代金だけを当座預金残高へ加える
→ 対象国債を共通担保から外す
→ 買い手へ国債を移す
```

返済と担保返戻の後でも、残りの共通担保が他の日銀与信、残存貸越、未約定予約を下回る場合は
全体を拒否する。日銀の基本要領も、担保中の国債の譲渡と同時に受け取る資金で貸越を返済する
扱いを定めている [1]。

## 6. 同時RFQと二重使用の防止

各法人状態には単調増加する通し番号を持たせる。予約、担保追加、再評価、DVP、日末処理は、
読み取った直前番号を必ず指定する。

例として、利用可能額が970百万円の法人へ、700百万円と300百万円のRFQが同時に来た場合を考える。

1. 700百万円の予約が先に合意され、法人番号が `n` から `n+1` になる。
2. 同じ `n` を前提にした300百万円の予約は古い状態として拒否される。
3. 300百万円側が `n+1` を読み直して再提出しても、残余270百万円を超えるため拒否される。

これはリクエスト元のウォレット数に依存しない。同じ法人の支店、担当部署、複数の取引端末から
提出された要求は、同じ法人要約IDの共通担保へ合算される。

予約は見積もり後の追加署名を要求するためのものではない。TakerがRFQ送信時に自動決済へ事前同意し、
MPCが勝者を決めた後は、対応する予約を一度だけ消費して決済まで進める。期限切れまたは不成立なら
予約を返す。

## 7. 取消しと失敗

日銀ネットの利用細則では、必要な証券・資金指図がそろい、条件を満たした時点で同時処理する。
実行前の指図は取消し得るが、実行済みの片脚だけを戻す処理ではない。不足があれば実行せず、
未処理指図は所定時刻後に取消される [3]。

DeFMIでも境界を同じように分ける。

- `prepared`: 資産・担保余力を予約したが、まだ権利移転していない。期限前の明示取消しまたは
  期限切れ返却が可能。
- `armed`: 相手側の確定証明までそろった。安全性を優先し、片側だけを返却しない。
- `claimed`: 国債、担保、貸越、資金の正本更新が完了した。
- `refunded`: `armed`になる前に予約を返した。

同じAvalanche L1内の日銀型DVPは一つの合意トランザクションなので、条件不足、古い通し番号、
重複指図、期限切れのいずれでも状態根は変わらない。

## 8. 実際の日銀ネットとクロスDeFMIの違い

実際の日銀ネットでは、日銀が国債台帳と当座預金台帳を一体運営するため、同じ運営境界内で
原子的に処理できる [2]。一方、日本の国債DeFMIと米国の資金DeFMIなど、独立したAvalanche L1を
またぐ場合は、単一データベース取引を使えない。

クロスDeFMIでは次が追加で必要になる。

1. 各L1で別々の非公開脚IDを使って予約する。
2. 各L1の確定状態を、登録済み委員会のk-of-n署名付き証明にする。
3. 相手L1専用の結合値を使い、公開証明から共通取引IDを逆引きできないようにする。
4. 両側の予約と確定証明がそろった場合だけ`armed`にする。
5. `armed`後は可用性障害があっても片側返却を許さず、復旧後に`claim`を続ける。

したがって、日銀型処理を模倣する日本DeFMIと、異なる法域のDeFMIをつなぐ仕組みは同じものではない。
前者は中央銀行内の国債・担保・資金の一括更新、後者は独立した正本間の確定証明交換である。

## 9. Rust実装との対応

### 中核状態機械

- `rust/qomm-defmi/src/central_bank_liquidity.rs`
  - `BojLiquidityBook`: 法人、国債担保、予約、完了決済、使用済み入金・操作ID
  - `JgbCollateralLot`: 額面、時価、物価連動係数、掛目、評価版、担保状態
  - `ReserveIntradayLiquidity`: 法人単位の貸越余力予約
  - `SimultaneousCollateralDvp`: 国債、担保、貸越、資金の一括更新
  - `ReturnCollateral`: 他の貸越・日銀与信・予約を控除しても足りる場合だけ担保を返す
  - `ApplyFundsReceipt`: 同じ入金の二重利用を拒み、入金を貸越返済へ先に充てる
  - `UpdateOtherSecuredExposure`: 共通担保を使う他の日銀与信を法人単位で増減する
  - `EndBusinessDay` / `OpenBusinessDay`: 残存貸越の延滞分類と、完済後の翌営業日開始

全公開操作は、複製した次状態へ適用し、構造検査に通った場合だけ正本へ入れ替える。ライブラリを
Avalanche VMの外で使っても、失敗時の部分更新は残らない。

### Avalanche合意状態

- `rust/qomm-avalanche-vm/src/state.rs`
  - `State.boj_liquidity`が正本状態へ含まれる。
- `rust/qomm-avalanche-vm/src/execution.rs`
  - `defmivm.issueBojParticipant`
  - `defmivm.issueBojCollateralPledge`
  - `defmivm.issueBojCollateralRevalue`
  - `defmivm.issueBojIntradayReserve`
  - `defmivm.issueBojIntradayRelease`
  - `defmivm.issueBojCollateralReturn`
  - `defmivm.issueBojFundsReceipt`
  - `defmivm.issueBojOtherExposure`
  - `defmivm.issueBojSimultaneousDvp`
  - `defmivm.issueBojEndOfDay`
  - `defmivm.issueBojOpenBusinessDay`
- `rust/qomm-avalanche-vm/src/vm.rs`
  - `defmivm.bojLiquidity`
  - `defmivm.bojParticipant`
  - `defmivm.bojCollateral`
  - `defmivm.bojReservation`

発行操作は既存のk-of-n合意承認、直前状態根、操作IDへ結び付く。照会は受理済みブロック高、
受理時刻、ブロックID、状態根を返す。

### DSLと有限状態検査

- `defmi_schemas/japan_jgb.defmi`
  - `BOJ_COMMON_COLLATERAL`を法人単位、終業時期限として宣言する。
- `rust/qomm-defmi-dsl`
  - 中央銀行が運営する国債台帳と中央銀行マネー台帳だけを施設へ結べる。
  - 新規与信の担保内収まり、予約合計、同時DVP、日末分類を検査する。
- `defmi_schemas/compiled/JP_JGB.*`
  - コンパイル済みJSON、検証証明書、TLA+モデルを生成する。

有限状態検査は、価格下落による担保不足そのものを禁止しない。担保不足が起きた後の新規与信を
禁止し、追加担保または返済で回復できることをモデル化する。これは「常に担保価額が債務以上」と
仮定するより現実的である。

## 10. 現時点で模倣していないもの

次は外部制度または運用接続であり、現時点のRust状態機械には含めていない。

- 実際の日銀ネットへの接続
- 日銀が配布する銘柄別価格・掛目データの自動取込
- 適格担保の全銘柄マスターと法的担保権の実設定
- 基準貸付利率に連動する延滞利息額の自動計算
- 日銀営業日の締切時刻、障害時手順、手作業代替の全再現
- 実在参加者の口座・法人情報
- 日銀の規程または法的最終性をDeFMIへそのまま移せるという法的判断

この実装が再現するのは、公開資料から確認できる主要な会計関係と安全条件である。日本銀行または
実在CSDのシステムであるとは主張しない。
