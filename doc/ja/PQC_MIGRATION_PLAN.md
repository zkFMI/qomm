# QOMM / DeKYX / DeCCP / DeFMI 耐量子暗号移行計画

## 1. 目的

QOMM、DeKYX、DeCCP、DeFMIの現在の実装を完成・固定した後に、既存利用者と既存データを壊さず、通信、署名、本人・法人確認、決済承認、公開監査を段階的に耐量子化する。

この計画でいう「耐量子化」は、単に暗号ライブラリを交換することではない。次をすべて対象にする。

- 将来、保存済み通信を復号される危険への対策
- 将来、参加者・MPCノード・DeCCP・DeFMIの署名を偽造される危険への対策
- 鍵の更新、失効、アルゴリズム切替、複数DeFMI間の相互運用
- 現行ZK証明が耐量子ではないことを明示したうえでの、公開監査方式の移行
- 即時取引の速度と、長期間保存する金融記録の安全性の両立

DeKYXは、人・法人・機器・AIエージェントなど、参加主体に応じた確認を共通化する分散型の資格基盤を指す。法人確認はDeKYXのKYB機能として扱い、勝手に別製品・別リポジトリへ分離または改名しない。

## 2. 開始条件

PQC実装は、次の条件を満たした時点で開始する。

1. QOMM、DeKYX、DeCCPの現行機能が、それぞれの受入試験を通過している。
2. QOMMからzkPIを生成し、DeCCPの保証枠を消費し、DeFMIで決済する一連の処理が動作している。
3. 同時RFQ、枠超過、再送、二重決済、MPCノード停止、クロスDeFMI DvP/PvPの基準動作が固定されている。
4. 各リポジトリの基準コミット、プロトコル版、測定条件、現在の性能値を記録している。
5. 既存の公開鍵、署名、暗号文、ZK証明、ハッシュ、鍵保管場所を一覧化している。

PQC対応のために現行機能の意味を変えない。性能比較の基準となる現行版を先にタグ付けする。

**2026-09-05時点の状況:** この開始条件は未達である。OCLOBとDeFMIの決済経路は別タスクで実装・検証中であり、現行動作の完成・固定を完了したとは扱わない。ただし、現行サービスの動作を一切変更しない独立したP0の共通境界・棚卸しだけは先行する。新規 `zkfmi-crypto` の実装と読み取り専用の棚卸しは既存クレートへの依存追加、pin更新、TLS設定、zkPI保存形式の変更を伴わないためである。P1以降の配線をこの例外で開始しない。

## 3. 基本方針

用途ごとに方式を使い分ける。

| 用途 | 初期候補 | 適用方針 |
| --- | --- | --- |
| ノード間の接続 | X25519 + ML-KEM-768 | 移行中は両方から得た鍵材料を組み合わせる。接続ごとに確立し、注文ごとには行わない |
| 即時の取引・決済承認 | 現行署名 + ML-DSA-65 | 移行中は両方を必須とする。`どちらか一方` では承認しない |
| k-of-n MPC承認 | 現行FROST + k個のML-DSA署名 | 標準的な耐量子しきい値署名が確立するまでは、独立したk署名を検証する |
| 長期保存する状態ルート | SLH-DSA候補 | 毎注文ではなく、日次・ブロック・決済期間単位のチェックポイントに使う |
| 注文・在庫の秘密計算 | 現行MPC | Shamir秘密分散自体より、通信認証・署名・コミットメントを優先して移行する |
| 公開監査 | ハッシュベースのまとめ証明候補 | 注文ごとではなく、一定期間の状態遷移をまとめて証明する |
| DeKYX資格提示 | 耐量子資格証明または短期トークン | 重い証明は登録・更新時に行い、注文時には短期かつ一回限りの提示を使う |

暗号方式はRustから利用でき、標準適合、一定時間実装、監査状況、ライセンス、Avalanche環境での動作を確認したものだけを採用する。Python実装を参照用として追加しない。Goが必要な場合もAvalancheGoとの既存境界に限定し、暗号処理本体はRustに置く。

## 4. 移行後の共通構造

### 4.1 鍵と法人IDを分離する

法人、MPCノード、DeCCP、DeFMIの識別子を、特定の公開鍵から直接作らない。各参加者は次を持つ。

- 変更されない参加者ID
- 用途別の鍵ID
- 暗号方式IDと版
- 公開鍵
- 有効開始時刻と失効時刻
- 失効状態
- 旧鍵から新鍵への更新証明
- DeKYXで確認された参加主体との対応関係

これにより鍵を変更しても、保証枠、在庫、口座、監査履歴を同じ法人へ引き継げる。

### 4.2 すべての署名対象を正規化する

同じ取引が異なるバイト列として署名されないよう、次を含む共通の正規形式を定義する。

- プロトコル名と版
- ネットワークID、DeFMIデプロイID、対象コントラクトID
- 取引種別
- 注文、quote、zkPI、保証枠予約、決済指図の識別子
- 単調増加番号または一回限りの値
- 有効期限
- 使用する暗号方式ID
- 本文のハッシュ

署名の用途を必ず分離し、quote署名を決済指図や鍵更新へ流用できないようにする。

### 4.3 ダウングレードを禁止する

移行中のハイブリッド署名は、現行署名と耐量子署名の両方が有効な場合だけ受理する。耐量子署名の検証失敗時に、現行署名だけで続行する自動フォールバックは禁止する。

方式の変更は、版付きのネットワーク設定と発効時刻で行う。未登録方式、古い鍵、失効済み鍵、未知の版は閉じた状態で拒否する。

## 5. 実装段階

### P0: 現行暗号の棚卸しと性能基準の固定

実装内容:

- QOMM、DeKYX、DeCCP、DeFMIの暗号利用箇所を機械可読な一覧にする。
- `CryptoProvider`、`Signer`、`Verifier`、`KemSession`、`ProofVerifier` のRust境界を定義する。
- メッセージ形式に暗号方式ID、鍵ID、版を追加する。ただし現行版の動作は変えない。
- 現行の一件あたりバイト数、署名・検証時間、取引件数、CPU、メモリ、7ノードWAN遅延を測る。
- 現行ZK、曲線署名、鍵交換、ハッシュのうち、量子計算機に対して残らない保証を明記する。

**先行P0の実装（2026-09-05）:** 独立したRust workspace / crate `zkfmi-crypto` を `/Users/shukob/Research/DeFMI/zkfmi-crypto/` に作成した。版付きsuite、用途別KeyRecord、正規署名対象、バイト列のSigner / Verifier / KemEncapsulator / KemDecapsulator / ProofVerifier / CryptoProvider、Ed25519 + ML-DSA-65のAND署名検証、X25519 + ML-KEM-768のHKDF-SHA256結合を実装した。未登録方式・未知の版を拒否し、秘密鍵はzeroizeする。既存クレートはまだ依存していない。GitHub上の `shukob/zkfmi-crypto` は認証無効のため未作成で、作成時の初期公開範囲はprivateとする。

`qomm/rust`、`defmi/rust`、`zkpi/rust` に複製されている共通クレートの統合が、P1で配線する前提である。将来の共有はdekyx-coreと同じGit URL + `rev` 固定とし、この先行作業では既存のCargo、Cargo.lock、Dockerfile、compose、pinを変更しない。KeyRecordは既存のPublicManifest / EncryptedKeyStoreやDeKYXの鍵エポックを置き換えない。スナップショットや初期登録の認可、DeKYX参照の正当性は既存サービスの責任として保持する。

棚卸し対象はqomm、zkpi、defmi、oclob、dekyx、deccp、aethelの7リポジトリ。新リポジトリの `inventory/crypto_inventory.json` を正本とし、Markdownをそこから生成する。2026-09-05の固定スナップショットでは507ファイル・1,032 primitiveエントリを収録し、独立したgrep照合で漏れ0件、余分0件を確認した。原本825ファイルのハッシュを保持する。発注時の件数の多くはsrc内の非ハッシュ参照集合と一致するため、src+tests全対象と区別し、残る不一致は `count_reconciliation.json` に明示する。

**候補と選定:** 次は2026-09-05の引き継ぎで固定した候補版である。採用した2クレートは実際の依存解決とDocker試験で確認した。

- 基準コミットと測定結果のハッシュが一致している。

### P1: 通信のハイブリッド耐量子化

実装内容:

- Taker、Maker法人モジュール、MPCノード、DeCCP、DeFMI間の持続接続にML-KEM-768を追加する。
- 現行の鍵交換結果とML-KEMの共有値を、用途を分離した鍵導出処理へ入力する。
- 接続確立後の注文メッセージには共通鍵暗号を使い、注文ごとのKEM実行を避ける。
- 再接続、鍵更新、片側だけが新方式に対応する場合、改ざんされた方式一覧を試験する。

**実装前提の記録（2026-09-05引き継ぎ）:** Ubuntu 24.04ホストとbookwormベース環境のOpenSSL 3.0.13系には、対象の耐量子TLS群がない。openssl crate 0.10.81は `set_groups_list` を提供する。openssl-sys 0.9.117の `vendored` はopenssl-src ^300.2を使うため、OpenSSL 3.5系を同梱する300.xの具体版をロックして、ベースイメージを変えずに `X25519MLKEM768` を利用する構成をP1で検証する。

P1ではacceptorとconnectorの双方で `set_groups_list("X25519MLKEM768")` に群を固定し、古典群へ落ちるネゴシエーションを拒否する。これは鍵交換側の変更であり、TLS認証側の方式とは別である。引き継ぎ時点ではハイブリッド署名の標準方式を採用する前提を置けないため、ML-DSA証明書単独にするか二重証明書にするかを判断事項として残す。先行P0ではこれらの設定・証明書・通信コードを変更しない。

完了条件:

- 保存された通信を将来復号する攻撃に対して、片方の鍵交換が破られてもセッション鍵が直ちに復元されない構成になっている。
- 方式を弱いものへ落とす通信が拒否される。
- 現行7ノードWAN性能からの差分が計測されている。

### P2: zkPIとDeFMI決済承認のハイブリッド署名

実装内容:

- 各MPCノードにML-DSA-65鍵を追加し、DeKYXで確認された法人・運営主体と結び付ける。
- zkPIに現行FROST署名と、承認したkノードのML-DSA署名を格納する。
- DeFMIは、登録された同一委員会の異なるkノードが、同一の正規化済みzkPIへ署名したことを確認する。
- ノード重複、古い委員会、古い鍵、署名の差替え、別DeFMIへの再利用を拒否する。
- 署名本体を台帳へ全件保存する方式と、一定件数のMerkleルートへまとめる方式を比較する。

完了条件:

- 量子計算機で現行曲線署名が破られる想定でも、kノード未満では新しいzkPIを承認できない。
- 同時RFQ、保証枠消費、在庫ロック、決済の順序が現行版と一致する。
- 一件あたりサイズ、検証時間、Avalanche VMのブロック使用量が基準内である。

### P3: DeKYXの耐量子化

実装内容:

- 発行者、法人、失効リスト、参加者モジュールの鍵を版付きで管理する。
- 法人確認済みであること、許可市場、保証上限、資格期限を、必要以上の法人情報を公開せず提示できる方式を実装する。
- 重い資格証明は登録・更新時に生成し、取引時には短期・一回限り・用途限定の耐量子署名付き資格を使用する案を比較する。
- 同じ法人が複数ウォレットを使って制限を回避できないよう、法人単位の識別と失効を保つ。
- 量子耐性のない匿名資格を使う期間は、保証範囲を表示上・文書上で明確に分離する。

完了条件:

- 法人名を取引相手や市場運営者へ不要に公開せず、許可・上限・失効を検証できる。
- 失効、鍵更新、再登録、複数ウォレット、期限切れを通した実試験がある。
- 注文時の追加処理が即時取引を妨げない。

### P4: DeCCP、保証枠、担保、クロスDeFMI決済

実装内容:

- 保証枠設定、国債担保差入れ、当座貸越、証拠金、ネッティング結果、デフォルト処理へ耐量子署名を追加する。
- 枠予約と消費を同じ法人IDへ結び付け、鍵更新による二重枠取得を防ぐ。
- 日本側・米国側など異なるDeFMI間のDvP/PvPで、双方の状態ルート、時刻、資産、金額、取消条件へ署名する。
- 中央銀行、CSD、商業銀行、証券会社の各役割を、別の鍵用途と承認規則として表現する。
- USDC等を資金側に使う場合は、外部チェーンの確定性と鍵方式を別の信頼境界として記録する。

完了条件:

- 片側だけの決済、古い状態ルート、別取引への署名流用、鍵更新中の二重決済を拒否する。
- MPCノード停止時の法人側キューから、鍵の有効期限内に安全に再送できる。
- クロスDeFMI DvP/PvPとPvPの障害試験で、資産または資金だけが確定しない。

### P5: 公開監査用ZKの耐量子化

これは署名移行後に行う。注文ごとの重い証明は初期要件にしない。

実装内容:

- 現行ZKが保証する事項を、入力範囲、価格ポリシー、勝者選択、在庫更新、保証枠保存、決済保存則に分解する。
- どの情報をk-of-n MPC署名で保証し、どの情報を誰でも検証できる証明にするか決める。
- 一定期間の複数zkPIとDeFMI状態遷移を一つのハッシュベース証明へまとめる。
- 失敗時に問い合わせの有無を漏らさない固定間隔の証明生成を検討する。
- 証明方式の実装、監査状況、証明サイズ、生成時間、検証時間、並列化、GPU依存を比較する。

完了条件:

- 現行ZKを外しても同じ公開検証事項を満たすか、満たさない項目が明記されている。
- 一件ごとではなくバッチ単位で、即時処理と分離して証明できる。
- 証明生成停止が取引内容や問い合わせ発生を外部へ漏らさない。

### P6: 現行方式の終了

実装内容:

- 全参加者の対応率、旧鍵で未決済の取引、長期保存記録、災害復旧手順を確認する。
- 移行期間終了後は、現行署名だけの新規メッセージを拒否する。
- 過去記録について、耐量子署名付きチェックポイントを作る。ただし過去の非耐量子署名が当時から耐量子だったとは扱わない。
- 緊急設定変更にも複数主体の耐量子承認を要求する。

完了条件:

- 旧方式だけで新規取引、鍵更新、保証枠変更、決済を実行できない。
- 旧方式終了後の復旧訓練が成功している。
- 仕様、SDK、デモ、運用手順、脅威モデルが同じプロトコル版を示す。

## 6. 暫定性能基準

P0で測定した現行値を正本とし、以下を最初の合否基準とする。実測前に基準を緩めない。

- 注文・quote・zkPI・決済の処理件数: 現行版の95%以上
- オンライン経路の追加遅延: p95で5ミリ秒以下を目標、10ミリ秒を上限候補とする
- 通常の3-of-7 zkPI: 従来の16KB目標 / 32KB上限候補は、現行 `package_bytes` 57,971 Bの定義と対象範囲を確認したうえで再設定する。未確認のまま合否基準として適用しない
- KEM: 持続接続の確立・更新時だけ実行し、注文件数に比例させない
- 公開監査証明: 注文ごとに100KB級の証明を載せず、バッチ当たりの費用として測る
- DeKYX登録・更新: 秒単位を許容できるが、注文時提示はオンライン経路の基準内に収める
- Avalanche VM: ブロック容量、永続ストレージ増加、状態同期時間を必ず測る

**現行値とサイズ算術（2026-09-05引き継ぎ）:** 既存artifactsの集計では `package_bytes` 57,971 Bが23件、57,939 Bが3件で一致し、小さい系は5,988〜7,268 Bだった。`proof_bytes` には33,024 B / 4,352 Bなどがあり、packageとproofは同じ量ではない。従来の16KB / 32KBはpackageの定義によって既に超えているため、耐量子署名の追加分だけを主因とみなさない。この表の暗号サイズはFIPS定数からの算術であり、新しい性能計測値ではない。

| 方式・構成 | 公開鍵 | 署名または暗号文 | 備考 |
| --- | ---: | ---: | --- |
| ML-KEM-768 | 1,184 B | 1,088 B | 展開済みdkは2,400 B。seed保存形式とは区別する |
| ML-DSA-44 | 1,312 B | 2,420 B | 単独署名 |
| ML-DSA-65 | 1,952 B | 3,309 B | 単独署名 |
| ML-DSA-87 | 2,592 B | 4,627 B | 比較用定数 |
| SLH-DSA-SHA2-128s | 32 B | 7,856 B | 長期チェックポイント候補 |
| 3-of-7 / ML-DSA-65を3本 | — | 9,927 B | 3 × 3,309。既存署名やメタデータは含まない |
| 3-of-7 / ML-DSA-44を3本 | — | 7,260 B | 3 × 2,420。既存署名やメタデータは含まない |

追加の署名・検証時間、スループット、メモリ、7ノードWAN遅延はこの先行P0では測っていない。上記の目標値を実測値として引用しない。

性能基準を満たせない場合は、安全性を落とさず、署名のMerkle集約、接続の再利用、検証の並列化、バッチ証明の間隔を調整する。耐量子検証を省略するフォールバックは行わない。

## 7. 試験計画

重いビルド、テスト、性能測定はローカルMacで実行せず、OmenXまたはSoftBankのDocker環境で行う。

最低限、次を自動化する。

- NIST既知解との一致
- Rust実装間および保存形式の相互運用
- 1、3、7ノード構成とk未満・k以上の承認
- 7ノードWANでの通常時、遅延、切断、再接続、ノード停止
- 同時RFQ、同一法人の合計枠超過、在庫競合、再送、順序逆転
- 古い鍵、失効鍵、未知方式、重複署名、別ネットワークへの再利用
- ハイブリッド署名の片方だけが有効な場合の拒否
- DeCCP保証枠、国債担保、当座貸越、ネッティング、デフォルト処理
- 単一DeFMI、クロスDeFMI DvP、クロスDeFMI PvP、USDC資金leg
- キュー滞留中の鍵失効・期限切れ・プロトコル更新
- Avalanche VMの再起動、状態同期、スナップショット復元
- デスクトップと狭い画面のデモUIで、使用中の暗号方式、鍵版、承認状況を確認

各試験結果には、コミット、コンテナ画像のdigest、設定、入力seed、開始・終了時刻、結果、ログのハッシュを保存する。

## 9. 実装順の要約

```text
現行実装の完成
  -> P0 棚卸し・基準測定・共通境界
  -> P1 通信をハイブリッド化
  -> P2 zkPI / DeFMI承認をハイブリッド化
  -> P3 DeKYX資格と失効を耐量子化
  -> P4 DeCCP・担保・クロスDeFMIを耐量子化
  -> P5 公開監査証明をバッチで耐量子化
  -> P6 旧方式だけの新規処理を終了
```

最初の製品移行点はP4完了時とする。この時点では、即時決済の真正性はk-of-n耐量子署名で守り、公開ZK監査は現行方式と耐量子バッチ証明の移行途中であることを明示する。完全な耐量子公開監査を主張するのはP5の検証完了後に限る。
